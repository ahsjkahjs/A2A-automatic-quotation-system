Agent-to-Agent
Automated Quoting System

Built on the open A2A (Agent2Agent) protocol, buyer and supplier agents in separate organizations automatically complete the cross-enterprise loop of RFQ → quote → compare / negotiate → award → close & settlement. The LLM handles understanding, orchestration and negotiation; deterministic rules and pricing models own the pricing boundaries; humans keep control of every key decision.

01

Overview & Design Goals

The A2A automated quoting system upgrades the "person-to-person / portal-to-portal" RFQ and quoting process into "agent-to-agent" automated collaboration: each organization runs its own agent inside its security boundary, exchanging structured RFQs and quotes over an open protocol externally, while calling inventory, capacity, cost and pricing capabilities through tool interfaces internally. It does not let an LLM quote prices freely — it is a transaction infrastructure of protocol interoperability + deterministic pricing + controllable autonomy + end-to-end traceability.

GOAL · 01

Interoperable

Built on the open A2A protocol and JSON-Schema-based RFQ / Quote contracts, heterogeneous agents from different vendors and models can "plug and play" across organizations without point-to-point custom integration.

GOAL · 02

Automated

The LLM handles requirement understanding, task orchestration, multi-round clarification and negotiation; rules / pricing models handle available-to-promise checks and pricing. RFQ-to-quote is hands-free within SLA, escalating only on exceptions.

GOAL · 03

Trustworthy

Strong identity for organizations and agents, least privilege, sealed bids invisible before opening, verifiable credentials, and a tamper-evident audit trail across the full chain — preventing unauthorized quotes and bid rigging.

GOAL · 04

Reliable

Idempotency keys, timeout-and-retry, quote validity with price locking, Saga compensation and Outbox/Inbox guarantee eventual consistency for long cross-organization flows, with replayable and reconcilable failures.

GOAL · 05

Governable

Amount thresholds, automation boundaries, the human-in-the-loop (HITL) permission matrix, price guardrails and compliance screening are all policy-driven; the level of autonomy can be tuned by risk.

GOAL · 06

Extensible & Observable

A new supplier is discovered and onboarded simply by publishing an Agent Card; trace context propagates across agents so metrics, logs and conversations are trackable, replayable and measurable.

Core design principle — the LLM never sets price directly. The LLM handles unstructured information understanding, planning, multi-round clarification and negotiation language, and produces explainable narratives; the price figure is produced by deterministic rules / pricing models within an authorized range (floor price, target margin, discount authority). The LLM may only negotiate inside that feasible range. Any out-of-range request, below-cost red line or compliance hit is blocked by guardrails and escalated to a human, eliminating "the model making up prices" at the root.

FITS Typical scenarios

B2B raw-material / MRO / services procurement and supply-chain RFQs, tendering and reverse auctions, logistics and shipping freight rates, cloud-resource / API-style service transactions, insurance and financial-product quoting (the latter requires industry compliance and suitability overlays). Common traits: non-standard or semi-standard goods, multiple suppliers, multi-round negotiation, and deal sizes worth automating.

LIMITS Not applicable / use caution

Large or high-risk awards must never be fully automatic — they require HITL; highly standardized exchange-traded contracts should be matched by an exchange engine rather than A2A negotiation; heavily regulated products stay closed to automated quoting until compliance is in place; A2A targets task-level long-lived conversations, not millisecond market making, which needs dedicated low-latency systems.

02

Actors & Trust Boundaries

The system consists of "three organizational domains + cross-cutting trust authorities": the buyer domain and several supplier domains each run agents inside their own private boundary; the marketplace operator only provides neutral discovery, matching and witnessing and never touches anyone's cost / floor price or other trade secrets; identity and approval capabilities cut across all domains.

BUYER DOMAIN

Buyer Agent

Requirement parsing and RFQ authoring, sourcing strategy, supplier discovery and eligibility pre-screening, multi-attribute comparison, counter-offer strategy, award recommendation; integrates with procurement / finance systems.

SUPPLIER DOMAIN ×N

Supplier Agent

Intake of RFQs, pre-qualification, available-to-promise (ATP) / capacity / inventory checks, cost build-up and pricing, generating and submitting quotes, participating in multi-round negotiation.

NEUTRAL PARTY

Marketplace Operator / Orchestrator

Runs the registration directory and capability marketplace, organizes RFQ / bidding sessions, manages deadlines and bid opening, provides a neutral clock and audit witness; does not participate in pricing.

DISCOVERY

Registry

Hosts each agent's Agent Card (endpoint, skills, auth methods, streaming / push capabilities), verifiable credentials and reputation scores, powering capability matching and discovery.

TRUST

Identity & Trust Authority

Issues OIDC / OAuth2, mTLS certificates, DIDs and verifiable credentials (VC), binding each agent to its organization and providing the trust root for qualification, authorization and signing.

HUMAN-IN-THE-LOOP

Human Approval Nodes

Approvers on both sides: over-discount / over-amount quotes, new suppliers, abnormally low prices and large awards trigger a push notification for a human to approve or reject.

SYSTEMS OF RECORD

Enterprise Back-Office Systems

ERP / CRM / PIM catalog / WMS inventory / APS capacity / finance / FX, safely invoked by each agent through an MCP tool gateway; data never leaves the domain.

SETTLEMENT

Contract & Settlement

After award: contract / purchase-order generation, CA e-signature, fulfillment and acceptance, invoicing, payment or escrow, and four-party reconciliation.

04

End-to-End Process

An automated quoting transaction proceeds through four phases and 16 steps, with mandatory stage gates between phases. The happy path flows automatically between agents; when a risk condition is hit, the flow is escalated to a human at a gate or blocked, forming an autonomy model that is "automatic by default, with controllable boundaries".

PHASE 1
RFQ & Discovery
  • Structure the requirement and generate the RFQ (specs / quantity / lead time / terms / evaluation method / deadline)
  • Fetch Agent Cards; match suppliers by capability / region / category
  • Verify qualifications, credit and verifiable credentials (VC)
  • Fan out the RFQ task, sealed or open
PHASE 2
Intake & Quoting
  • Supplier pre-qualification and bid / no-bid decision
  • ATP / capacity / inventory checks; compute a promiseable lead time
  • Cost breakdown; the pricing engine bids within the authorized range
  • Guardrail checks; escalate beyond authority to a human; submit structured Quote
PHASE 3
Evaluation & Award
  • Clarification Q&A and multi-round counter-offers; quote versions recorded
  • Open sealed bids at deadline, or run a live reverse auction
  • Normalize currency / tax / incoterms / lead time; TCO scoring
  • Produce an award recommendation; high-value / anomalous awards go to HITL
PHASE 4
Close & Fulfillment
  • Generate contract / purchase order (PO); CA e-signature
  • Order fulfillment, shipment and acceptance
  • Invoicing, payment or escrow
  • Four-party reconciliation; performance & reputation feedback; price learning
G1 Eligibility Gate: failed qualification / credit / sanctions screening → not invited or not accepted.
G2 Pricing Authority Gate: below the cost floor or beyond discount authority → blocked and escalated to HITL.
G3 Bid-Opening Gate: sealed bids are invisible to everyone before the deadline; threshold decryption opens them at the deadline.
G4 Award Gate: amount / anomaly / new-supplier conditions trigger human review; all others award automatically.
Every quote carries a validity period and an idempotency key: it lapses automatically when expired (no award / no order); once awarded, the price is locked within validity and converted to an order. If the winning supplier fails to fulfill after award, the plan falls back to the runner-up or triggers a compensation flow to re-run the RFQ (see §09).

A2A Protocol Interaction Sequence

Using a sealed RFQ from one buyer to two suppliers as an example, the diagram shows the cross-organization A2A message flow: discover via Agent Card, submit the RFQ as a JSON-RPC task, suppliers stream progress over SSE, complete pricing inside their private domain via MCP, push for human approval when authority is exceeded, and finally return structured quotes followed by multi-round negotiation and award.

Request / invocation (message/send, cancel, Award) Response / async notification (SSE, Artifact, push)
Long-running pricing and approvals are always asynchronous: the caller subscribes to SSE via message/stream, or first registers a webhook with tasks/pushNotificationConfig/set so the supplier pushes when the quote is ready or approval is pending, avoiding long-lived blocking connections; every request carries an idempotency key so retries never create duplicate quotes or duplicate awards.
06

Quoting Task State Machine

The complete states and transition conditions of a quoting task from draft to settlement/archive. During competition, quotes are sealed before the deadline; over-authority quotes enter an HITL approval branch; expired, withdrawn, cancelled, failed and non-winning quotes converge into exception terminal states; after close the task proceeds along the fulfillment chain, and a fulfillment failure triggers Saga compensation to fall back to the runner-up.

In progress HITL approval / sealed Award / fulfillment Exception terminal Compensation flow
State is persisted in the A2A Task and transaction-service stores; every transition is an event with an idempotency key written to an append-only event log (event sourcing), so any task can resume from a breakpoint, be replayed and audited. Sealed quotes are invisible to buyers, suppliers and the platform alike until the "open at deadline" transition triggers threshold decryption.
07

Pricing Engine

The pricing engine is the supplier agent's core: it is an "LLM language layer + deterministic decision pipeline + guardrails / approval routing" structure. The LLM only parses requirements and handles negotiation; the price is computed by rules, cost models and constrained optimization inside an authorized feasible region, with hard guardrails and HITL approval at the boundary.

INPUT Decision basis

  • RFQ elements: specs / quantity tiers / lead time / delivery location / incoterms
  • Cost data: BOM, raw materials, labor, logistics, taxes & duties (via MCP)
  • Supply capability: inventory, ATP, CTP capacity (via MCP)
  • Commercial context: customer tier, credit line, payment terms, historical deal prices
  • Market signals: market prices, FX, competitive posture, demand elasticity
  • Authorization boundaries: floor price, target margin, discount authority matrix

CORE Deterministic pricing decision pipeline

  • 1 · Eligibility & deliverability checks: in-scope category, ATP/CTP, MOQ, lead-time feasibility
  • 2 · Cost build-up: cost breakdown (tax-inclusive / landed / total cost of ownership)
  • 3 · Pricing strategy: cost-plus / value-based / competitive / dynamic, with quantity tiers, bundling, payment-term combos
  • 4 · Constraint solving & guardrails: price floor, target margin, authority matrix, validity lock, dumping / controlled-price / price-discrimination compliance
  • 5 · Multi-objective trade-off: feasible optimum across margin × win-rate × capacity utilization × risk
  • 6 · Approval routing: per the authority matrix, auto-send or escalate to HITL
LLM boundary (negotiation layer only — it does not set price)

Parses unstructured RFQs / drawings, handles clarification Q&A, negotiation language and concession pacing, and produces explainable narratives; it may only negotiate within the feasible price range set in step 4. Any out-of-range, below-cost or compliance-hit request is blocked and routed to a human.

OUTPUT Structured quote

  • Quote body: unit / tiered / total price, currency, taxes, incoterms, lead time, validity
  • Pricing rationale: cost breakdown and pricing reason (explainable, auditable)
  • Confidence: win probability and price-elasticity estimate
  • Counter-offer playbook: concession pacing and walk-away (floor never leaves the domain)
  • Approval decision: auto-approved / escalated, with reason
  • A2A Artifact: signed, versioned quote artifact
Why not let the LLM quote directly? A pricing error is a direct, quantifiable and hard-to-recover financial loss, and LLM output is non-deterministic and easily swayed by negotiation language. Converging pricing to "rules / optimization models solving a feasible region + hard guardrail constraints", with the LLM handling the language layer inside that region, keeps natural interaction while making every quote recomputable, explainable and accountable.
08

Trust, Security & Governance

Cross-organization automated trading presupposes provable fairness, controllable autonomy and traceable accountability. Trust does not rely on assuming any party's goodwill; it is guaranteed jointly by identity, cryptography, risk control, permission boundaries and audit.

IDENTITY

Strong Identity & Least Privilege

The Agent Card is bound to the organization's DID / mTLS certificate; OAuth2/OIDC issues scoped tokens; every message is signed with nonce / timestamp to prevent replay; agent actions are attributable to the organization.

FAIRNESS

Sealed Bids & Fair Opening

Before the deadline quotes are public-key encrypted or sealed inside a TEE, invisible to buyer, suppliers and platform; a trusted timestamp is used and threshold decryption / opening happens only at the deadline, preventing early leaks and covert price changes.

ANTI-FRAUD

Risk Control & Anti-Collusion

Detect near-identical quotes, related parties, IP / account clustering, abnormally low prices or cover-bidding patterns; build a supplier relationship graph; a collusion hit freezes the award and routes to compliance investigation.

AUTONOMY BOUNDARY

Autonomy Boundary & HITL

Configure the permission matrix by amount, discount depth, anomaly, supplier novelty and term deviation; in-policy actions run automatically, out-of-bounds actions escalate, red-line actions are denied outright.

CONFIDENTIALITY

Trade Secrets & Data Minimization

Cost, floor price, capacity and customer lists stay in each private domain; pricing completes locally; only authorized RFQ / Quote messages and necessary credentials cross domains, following data minimization and data sovereignty.

AUDITABILITY

End-to-End Audit & Explainability

RFQs, quotes, counter-offers, pricing rationale, approvals, bid opening and awards are all written to an append-only, hash-chained audit log — replayable, evidentiary and ready for regulatory inspection.

Human-in-the-Loop (HITL) Autonomy Permission Matrix — thresholds are configured per enterprise policy; the table below is an illustrative policy framework

Sealed-bid implementation notes: the buyer's public key (or a TEE public key) encrypts each quote; the platform stores only ciphertext plus a trusted timestamp. After the RFQ deadline, the key becomes usable only via a threshold scheme (e.g. multi-party threshold signatures / TEE remote attestation), so no single party can decrypt anything before the deadline. The opening event and participant signatures are written on-chain / into the hash-chained log, letting every party independently verify that quotes were not tampered with and the opening was not advanced.
09

Reliability & Cross-Organization Consistency

Cross-organization long transactions face unreliable networks, heterogeneous systems and partial failures. Reliability is not built on "every call succeeds", but on a set of distributed-consistency patterns that make failures replayable, operations idempotent and state eventually consistent.

PATTERN · 01

Idempotency-Key Dedup

Every RFQ, quote, counter-offer, award and order carries a globally unique Idempotency-Key; the receiver stores the key + result, so retries return the same result and never create duplicate quotes / orders / awards.

PATTERN · 02

Async-First with Timeout Fallback

Long tasks never hold a blocking connection; they use SSE or webhook push with bounded waits. On timeout, query task status rather than blindly resubmit; a dead-letter queue (DLQ) plus alerting handles lost messages.

PATTERN · 03

Transactional Outbox / Inbox

The sender atomically writes the business change and the message to an Outbox, then a relay publishes it; the receiver writes to an Inbox for dedup, guaranteeing "at-least-once delivery + idempotent processing = effectively once".

PATTERN · 04

Saga Compensation over Long Transactions

Award → contract → fulfillment is split into local transactions with compensation actions; a failure (e.g. winner cannot fulfill) triggers compensation: cancel PO → fall back to runner-up / re-run RFQ, rather than a distributed two-phase commit.

PATTERN · 05

Validity & Price Lock

Every quote carries validity; within validity the supplier honors the locked price and stock; after expiry it lapses or is re-confirmed; at award the price is locked to prevent "quote ≠ order price" disputes.

PATTERN · 06

Reconciliation & Replay

Scheduled reconciliation across buyer, supplier, platform and settlement (four-party), with the event log / conversation log as the source of truth; discrepancies auto-alert and are replayed to the last consistent point.

Agents are not centralized on one platform; each organization runs its own agent inside its own security boundary and only exposes an A2A endpoint outward, while the marketplace provides neutral discovery, matching and sealed-bid witnessing. Phased Rollout Roadmap

Deliver in five milestones from point-to-point connection to a federated network. Each milestone ships standalone value; autonomy and trust mechanisms are introduced progressively rather than all at once.

M1 · 0–2 mo

Point-to-point connected

One buyer + one supplier; Agent Card discovery; RFQ / quote over A2A; basic rule-based pricing; manual approval; the happy path works end to end.

M2 · 2–4 mo

Multi-supplier comparison

Fan out RFQs to N suppliers; quote normalization and TCO comparison; SSE + webhook; idempotency / Outbox; validity and price locking.

M3 · 4–6 mo

Autonomy & bidding

Pricing engine with multi-objective optimization; multi-round negotiation; authority-matrix HITL; MCP integration with ERP / WMS / APS; rules engine.

M4 · 6–9 mo

Trusted closed loop

Sealed bids + TEE / threshold opening; risk control & anti-collusion; Saga compensation; contract / PO / e-signature / reconciliation; full audit trail.

M5 · 9–12 mo

Scale & federation

Multi-tenant / multi-region; reputation and credential network; reverse auction / dynamic pricing; industry templates; federated governance and compliance certification.

Do not wait for the full trust / federation stack to launch: M1–M2 already replace most manual email / portal quoting; M3–M4 raise autonomy and trust; M5 turns the system into a network effect.

Protocol Split & Data Contracts

A2A and MCP are complementary, not competing: A2A is the external "inter-agent collaboration language" across organizations; MCP is the internal "agent-to-tool / data interface" inside an organization. Exposing internal cost tools directly to external agents, or using MCP for cross-organization negotiation, breaks both the trust boundary and the protocol boundary.

A2A — Agent ↔ Agent cross-organization

  • Scope: cross-organization, cross-trust-domain task collaboration
  • Carries: RFQ, Quote, negotiation, award and other business tasks (Task / Message / Artifact)
  • Stateful, long-lived, multi-turn, async streaming / push
  • Identity: organization-level DID / mTLS / verifiable credentials
  • Example: buyer agent → supplier agent: "quote these 500 parts, reply within 3 days"

MCP — Agent ↔ Tools / Data inside organization

  • Scope: an agent connecting to internal tools and data within one trust domain
  • Carries: tool discovery and invocation (resources / tools / prompts)
  • Usually short request / response; exposes capabilities, not business conversations
  • Identity: internal service accounts / least-privilege scopes
  • Example: supplier agent → internal ERP: "query inventory and standard cost for SKU-123"
Data-contract boundary: cross-domain messages carry only the RFQ and the Quote (business semantics); internal cost build-up, floor price, capacity and customer master data are invoked by the agent through MCP inside the private domain and are never serialized into A2A messages. This keeps the external protocol minimal and stable while internal systems can evolve freely.
